# Safe Rails migrations

## Before
1. `bin/rails db:migrate:status` shows what has already run.
2. **Never edit a migration that is committed or shows `up`.** Create a new one:
   `bin/rails g migration AddStatusToOrders status:string`
3. Never hand-edit `db/schema.rb` / `db/structure.sql`; they are regenerated by `db:migrate`.

## Writing it
- Prefer `change` with reversible methods. Use `up`/`down` (or `reversible`) only for irreversible operations, and make `down` real or `raise ActiveRecord::IrreversibleMigration`.
- Pass explicit types to `remove_column` (`remove_column :users, :age, :integer`) so it can be reversed.
- Constraints belong in the DB and the model: `null: false`, `default:`, `add_index ..., unique: true`, `add_foreign_key` / `t.references ..., foreign_key: true`.
- Postgres, large tables:
  - Add indexes with `algorithm: :concurrently` + `disable_ddl_transaction!`.
  - For a NOT NULL column on existing rows: add it nullable, backfill in batches, then add the constraint in a follow-up migration.
  - Don't rename or remove a column in one step while code still reads it. Use `ignored_columns` first.
- Data backfills: use `in_batches` and don't reference app models (define a lightweight `Class.new(ActiveRecord::Base)` inside the migration). Better still, use a separate rake task.

## After
1. `bin/rails db:migrate` then `bin/rails db:migrate:status`
2. Check the schema diff: `git diff db/schema.rb`. Only the intended changes should appear.
3. Prove reversibility **only if the user agrees** (the guard will ask): `bin/rails db:rollback && bin/rails db:migrate`
4. `bin/rails db:test:prepare && bin/rails test`

## Forbidden without explicit user request
`db:drop`, `db:reset`, `db:schema:load`, `db:migrate:reset`, `db:rollback`, `db:seed:replant`, raw `DROP`/`TRUNCATE`.
The dev database may hold data the user cares about, and it isn't in git.
